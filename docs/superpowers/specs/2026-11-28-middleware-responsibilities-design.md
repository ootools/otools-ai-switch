# 中间件职责、配置规则与执行阶段重整

日期：2026-11-28
状态：用户已选择并批准三个独立插件方案；实现与验证已完成，具体交付记录见对应实施计划。
范围：接续紧凑列表改造，解决用户提出的五项语义与可用性问题。

## 已核实的问题

1. `src/lib/pipeline.ts:createDefaultPipeline` 将全部 18 个内置插件放入账号列表，即使没有启用；目录与已添加列表混在一起。
2. `builtin.schedule.*` 的 8 个条目多数只是一个策略字段，重试、续写和账号健康被拆得过细。
3. `builtin.response.plaintextReasoning`、`crossResourceStrip`、`encryptedContentCleanup` 实际在上游请求发送前修改 input，而非下游响应。依据 `route_proxy_service.rs` 的 postBridgeCross/postBridgePlaintext/postBridgeEncrypted 调用和脚本 onRequest 实现。
4. `plugin_middleware.rs:apply_chain` 按固定 stage 调度；列表顺序只影响同一阶段，当前“从上到下执行”并不准确。
5. `builtin_plugins.rs:compute_policy` 从旧 failure_policy 或原生默认值开始叠加启用插件。因此移除/禁用某插件不保证对应功能停止；仓储失败记账又直接读取旧 failure_policy，存在前后端和运行路径不一致。
6. 路由中还存在不受对应插件开关约束的自愈分支，例如加密失败后清理重试、图片超限后裁剪并自动启用。需一并核对，避免删掉插件仍发生请求改写。
7. 错误分类散落在 response_failure_service、route_proxy_service；HTTP 200 也可能包着 JSON/SSE 错误。不能仅列 HTTP 状态码；现状同账号重试也不只是 408/429/5xx。

## 推荐的插件边界

| 插件 | 解决的问题 | 纳入的旧条目/配置 | 执行阶段 |
| --- | --- | --- | --- |
| 失败重试 | 上游临时失败，在还没有把正文交给客户端时重试；耗尽后可换账号 | retry、failover、streamPrelude | 调用失败处理；首次输出前 |
| 流式恢复 | 已输出部分内容后，流中报错或连接中断，尝试续接剩余内容 | streamSalvage、streamContinue | 流式响应观察 + 后续请求 |
| 账号故障处理 | 连续失败后暂时避开故障账号或标记异常 | cooldown、errorStatus、semanticThreshold | 失败记账 + 后续账号选择 |
| 请求加密内容清理 | 避免下一轮请求携带的 reasoning.encrypted_content 无效/无法跨服务验证 | encryptedContentCleanup | 请求发送前 |
| 跨服务历史状态清理 | 换资源后历史 ID/加密状态无法使用 | crossResourceStrip | 请求发送前 |
| 推理历史格式兼容 | 将重放请求中的 reasoning_text 转为上游接受的 summary_text | plaintextReasoning | 请求发送前 |

其余请求压缩、远程图片内联、图片数量兼容、自定义工具兼容等各自解决不同问题，保留独立添加；不为了缩减数量将内容丢失风险不同的改写合并启用。

备选：把前三个归为一个“失败与中断处理”插件，内部再分重试/续接/账号状态三个配置区。列表更短，但开关和移除粒度更粗，配置面板更大。推荐前三个独立。

## 用户看到的界面

- 主区域仅显示“已添加中间件”，沿用上一轮确认的紧凑列表、单项展开和独立开关。
- 每行展示：功能名称、解决的问题、状态、当前配置摘要、实际阶段标签。
- 阶段筛选为“全部 / 请求处理 / 响应处理 / 失败恢复”，不再把调用策略伪装成单向请求改写。
- “添加中间件”打开独立目录，支持搜索、按用途筛选；不把整个目录常驻在账号列表下。
- 目录只将未添加条目作为新增候选；已添加但关闭的条目可定位或重新启用，不能复制一份。
- 移除后保存并重开仍保持移除。恢复推荐配置是明确操作，不在每次读取时偷偷补齐。
- 固定阶段由运行时决定；只有同阶段可排序。策略项无虚假的执行序号。
- 详情按“解决什么 / 何时触发 / 会怎么改 / 当前规则 / 限制”组织。实现术语放在必要的字段解释里。

## 推荐默认项（新账号）

- 自动添加并开启“失败重试”：额外重试 2 次、间隔 200ms；首次有效输出前的建流帧最多等待 60000ms，解释为可重试窗口，而非网络连接超时；聚合模式支持失败换号。
- 自动添加并开启“账号故障处理”：连续失败阈值 10、异常标记开启、短暂冷却默认关闭（开启时默认 10 秒）。明确每个阈值用于何种失败，不把阈值描述成错误识别算法。
- “流式恢复”在目录内提供完整默认配置，添加时展示两个触发开关与续接上限；不默认启用会产生额外计费请求的续写。
- 主动清理请求内容、历史状态和图片等兼容功能按需添加；现有命中特定服务的兼容默认保留并说明匹配服务，不给所有服务一律启用。
- 旧账号保留其实际生效行为，不能仅按旧界面开关迁移，否则会误关隐含默认重试等能力。迁移结果把这些生效项显式显示出来。

## 流式恢复的两个触发条件

1. 上游明确报错：已经输出正文，随后收到 SSE error/response.failed 等错误；当前实现仅恢复容量不足、限流等瞬时错误。
2. 连接提前结束：已经输出正文，连接结束但没有正常终止标记；无需匹配错误码。

二者都通过携带已输出内容再次请求上游续写，并将续写拼接回同一条响应。它们不是原请求从字节偏移处恢复，每轮可能另行计费，也不能承诺完全无缝。

同一插件内分别启停，统一显示续接预算、等待间隔、总时限、是否允许换号；不能继续隐藏依赖另一个插件的重试次数。迁移保留旧行为的预算关系，迁移后配置显式独立。

保留既有不可续接条件：未形成可续写内容、超出保留大小、请求无法重建、加密推理过程无法安全续接、不支持的协议路径。详情应列出实际支持范围。

## 错误规则：可读、可配置、可验证

错误观察统一包含：HTTP 状态（可空）、结构化 error.code、error.type、error.message、连接错误类型、所在阶段（输出前/输出后）。正常正文中的词不能被当成错误消息匹配。

每条规则包含：名称、启停、优先级、条件组、动作和参数。默认规则直接显示完整值，不只显示“内置规则”。

- HTTP 状态：精确值、范围，例如 408、429、500–599。
- code/type：忽略大小写的精确匹配，可列多个值。
- 消息：包含、开头匹配；可忽略大小写，规范化空白；支持“同时包含”多个短语。
- 同组条件为 AND，多组为 OR；界面用“同时满足/任一组满足”解释。
- 动作：重试当前账号、转下个账号、直接返回错误；账号冷却/标记由账号故障处理插件配置，不用一个无差别“失败”标签隐式联动。
- 支持排除条件、规则排序、恢复默认值；首次版本不引入任意脚本或无界正则。
- 添加“测试错误样例”：输入状态和 JSON/SSE 错误，显示提取字段、命中规则和预计动作；沿用后端实际匹配器。
- 日志记录命中规则 ID/名称、错误类别、动作和本轮预算，便于理解为何重试或停止；避免额外复制敏感请求正文。

默认规则必须由后端同一数据源提供，不能前端写一套说明、后端另写一套条件。现有容量/限流及组合识别规则需完整迁移，包括：

- 容量 code：no_capacity、capacity_exceeded、insufficient_capacity、overloaded、overloaded_error、server_overloaded、model_overloaded、high_demand。
- 容量消息：high demand、peak load、provisioned throughput、no capacity、insufficient capacity、out of capacity、currently overloaded、servers are overloaded、model is overloaded、at capacity。
- 限流 code/type：rate_limit_exceeded、rate_limit_error、too_many_requests、requests_per_minute_limit、tokens_per_minute_limit。
- 限流消息：rate limit、too many requests、requests per minute、tokens per minute、please slow down。
- 区域吞吐限制：特定限流 code/type AND 明确 token rate limit 文案，并排除账单/额度信息；按容量处理，不误伤账号健康。
- 明确额度耗尽、权限不足、请求参数/上下文错误等保留专门识别，不被宽泛 429/5xx 规则覆盖。规则页说明为何不能靠原样重试解决。

新账号的重试默认采用明确允许项：连接瞬时错误、408、429、5xx、已识别的容量/限流错误（含 HTTP 200 内的错误）；未命中不盲目重复同一请求。旧账号若原来会重试其他语义错误/状态，迁移为可见的兼容规则，不能悄悄改变行为。

协议完整性限制与普通可编辑匹配规则分开：已经输出后不能直接整段重发、已完成的响应不能续接、401/403/明确永久凭据失效等不能被普通重试规则绕过。界面显示这类限制的原因；错误识别配置和协议安全限制不得混为一谈。

## 配置与运行时一致性

- 引入版本化的新配置，分别保存 request/response/recovery；内置 ID 的历史命名不能决定执行阶段。
- 统一有效策略解析器供代理、续接、仓储失败记账、导入导出使用。
- 显式新版本配置从全关闭基线构建；只有已添加且开启的插件提供行为。
- 旧配置迁移一次、幂等、保留第三方 pack 和未知配置；不得依赖仅 cfg(test) 生效的迁移 shim。
- 迁移优先保留实际有效参数、自动服务匹配、旧方向直通的语义和用户定制配置。
- 旧的错误方向迁移时保留此前是否真的执行，不能因为移动到请求分类而重新激活原来被响应直通禁用的改写。
- 未启用/已移除的加密清理、图片裁剪等不允许被失败分支自动重新启用或偷偷执行；必要的协议适配须独立说明其不属于可选中间件的原因。
- 清理仅针对请求里携带的加密状态，不虚构解密能力，也不默认删除正常响应里的推理信息。

## 验收重点

1. 新账号列表只出现推荐项；添加/禁用/移除/保存/重开语义一致，关闭就是不执行。
2. v1 真实配置迁移和再次读取一致，包含默认全量列表、定制关闭项、方向直通、第三方 pack、旧 failure_policy。
3. 状态/code/type/消息条件及 AND/OR/排除优先级有真实后端测试；覆盖 HTTP 200 错误、数字 code、缺失字段、中文消息及正常正文误匹配。
4. 输出前重试不会复制输出；输出后两类中断触发和预算各自正确；不可续接时保留有用原始错误。
5. 请求清理确实只在出站请求阶段，响应直通不再隐式控制它；关闭时包括错误自愈路径都不改写。
6. 故障记账与代理使用相同有效策略，容量错误不因误分类冷却账号。
7. 界面展示的默认值、命中样例和运行时结果一致；移动端/键盘操作/长规则内容不溢出。
8. 跑相关 Rust、前端单测、TypeScript 和生产构建；通过后再给真实界面预览。
